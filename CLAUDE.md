## 2. Stack

| Layer | Choice |
|---|---|
| Framework | Next.js **16** (App Router, RSC, React **19**) |
| Language | TypeScript 5.6, strict, `@/*` → repo root |
| Styling | Tailwind CSS **v4** (`@import "tailwindcss"`, no `tailwind.config.*`) |
| UI kit | shadcn/ui, style **`base-nova`**, built on **`@base-ui/react`** (NOT Radix) · **affectUI** AI components via the `@affectui` shadcn registry |
| Icons | `lucide-react` (brand icons are inline SVG, not lucide) |
| Auth | **CloudHike.dev Auth HTTP API** (better-auth was removed) |
| DB | **CloudHike Postgres** via Drizzle ORM + `postgres` driver |
| Agent runtime | **OpenAI Agents SDK** (`@openai/agents` + `openai`), provider-agnostic via OpenAI-compatible connections |
| External apps | **Composio** v3.1 REST (connect links) + hosted MCP tool-router sessions (no SDK dependency) |
| Cloud browser | **Browserbase** (`@browserbasehq/sdk`) + **Stagehand 4** (`@browserbasehq/stagehand`) — remote sessions, per-user Contexts |
| Schemas | `zod` (tool parameters, chat request validation) |
| Charts | `recharts` |
| Code highlight | `shiki` (`lib/highlighter.tsx`, `hooks/use-highlighted-code.ts`) |
| Markdown | `react-markdown` + `remark-gfm` + `remark-breaks` (chat replies) |

## 4. Auth Flow (CloudHike Auth)

CloudHike Auth is the source of truth for credentials/sessions. This project uses Auth's **managed storage** — there is no `auth` schema in the project Postgres (verified: only `public` exists). Our `public.users` table is an app-level mirror for joins and dashboards.

**Email / password**
1. `AuthForm` submits to `signUpAction` / `signInAction` (`app/actions/auth.ts`).
2. Action calls `signUpWithEmail` / `signInWithEmail` (`lib/auth.ts`) → `{ token: string | null, user }`.
3. `saveUser(user, "email")` upserts into `public.users`.
4. **`token` can be `null`**: this project has *Require a verified email* ON, so sign-up creates the user and emails a link but issues no session, and sign-in returns `403 Email not verified` until the link is opened. Both actions then set `state.notice` (rendered inline by `AuthForm`) instead of setting a cookie or redirecting.
5. With a token: set the http-only `cloudhike_session` cookie, then `redirect("/dashboard")`.

**Google / GitHub**
1. Sign-in/sign-up pages build a URL with `socialSignInUrl(provider, to)` where `to` is `/auth/callback?provider=...`.
2. Provider returns to `/auth/callback` with `#token=...` (fragment — never sent to a server).
3. That client page POSTs the token to `/api/auth/session`, which calls `getSessionUser`, runs `saveUser`, sets the cookie, then the client `router.replace("/dashboard")`.

**Guards:** `getCurrentUser()` in `lib/session.ts`; `requireUser()` redirects to `/sign-in`. `/dashboard` and both auth pages use them.

**CloudHike Auth API** (`lib/auth.ts`, all requests send `x-api-key: AUTH_PUBLISHABLE_KEY`):
`POST /sign-up/email`, `POST /sign-in/email`, `GET /get-session` (Bearer token), `POST /sign-out`, and browser-only `GET /social/<provider>?to=`.

A widget's own cron is not an agent schedule: `next_refresh_at` is the clock, `widget_refresh_runs` is the real history, and the legacy `schedule_id` column is kept for old rows only. `lib/widget-refresh.ts` is the read-only update behind every refresh: one Agents-SDK call with only the reading tools the agent has enabled (`web_search`, `read_webpage`, `calculate`) plus `save_widget_data`, whose payload is normalized in the tool; it can never touch the title, design, form, size or schedule. If that turn used a reading tool but ended without saving, it gets one more turn on the same conversation with **only** the save tool, so what it just read isn't thrown away. A turn-limit error after `save_widget_data` already ran is treated as success (the gateway can spend the limit on the saving step), and a failed retry keeps the old data. Refreshed data is merged field by field (`mergeWidgetData`): a field the sources didn't cover keeps its stored value, so one new metric can't wipe the chart or the list — the prompt says to leave unsupported fields empty instead of padding them, and the save tool says only the fields sent are replaced. A refresh that fails records an error run and keeps the last data. The widget card never fakes a chart from too little data: a payload with fewer than three real points resolves to a number (or another supported form), and a percent that disappears falls back to split/tiles rather than an unrelated trend. The illustrated style reserves header space for its chosen scene.
`widget-refresh-service.ts` has four entry points, all owner-safe except the Jobs one: `refreshWidgetForUser` ("Update now" from the dashboard or chat strip), `catchUpWidgetsForUser` (dashboard mount, only the most-overdue widget so one visit isn't blocked by three sequential model calls; `claimOverdueWidgets` moves `next_refresh_at` with a conditional UPDATE, so two tabs run each widget once), `refreshDueWidgets` (inline cron), and `refreshWidgetById` (the signed `/api/jobs/widgets` worker). The cron tick calls `listDueWidgetRefreshes(3)`, hands each to Jobs when configured (after `reserveWidgetRefresh`), and otherwise refreshes inline; paused workspaces contribute no widgets. `WidgetGrid` calls `catchUpWidgetsAction` once on mount and merges the returned records; `WidgetMenu` has "Update now" with a spinner and an error dialog; the agent panel reads `listWidgetRefreshRuns(profile.id, agent.id)` into a real "Widget updates" section.
**Approval modes** (`agents.approval_mode`, set from the chat composer's approval menu **and** the agent config rail's Approvals section via `updateAgentApprovalModeAction` → `setAgentApprovalModeForUser`): `ask` (default) shows the card for every data-changing action; `auto` runs an action without a card only when the owner already approved **that exact action on that toolkit for that agent** in the last 30 days (`hasRememberedApproval`); `full` runs every change without a card. Both automatic paths still write an `agent_approvals` row (`recordAutoApproval`, summary prefixed `[remembered]` / `[full access]`, status/`usedAt` set) so the log is as complete as a manual approval, and they push a normal result card. Scheduled runs read the same stored mode. The single-use token path is unchanged for `ask`. Settings shows the result as an **Approval log** card (`components/dashboard/approval-log.tsx` + `listApprovalLog`, newest 20): toolkit/action, one-line summary, agent, time, and a chip reading Approved / Remembered / Full access (the mode is derived from the stored `[remembered]` / `[full access]` prefix and stripped for display). Verified live against Postgres through a temporary route (since deleted): before a manual approval `hasRememberedApproval` was false, after approving `GMAIL_SEND_EMAIL` it was true, a different action and a different owner were both false, and the log listed the manual row as `approved` and the auto row as `remembered`. The real Composio execution under `auto`/`full` is still unexercised — it needs a signed-in chat with a connected account.
`agent_approvals` makes approval tokens single-use: `consumeApproval` performs a conditional UPDATE on `jti` + owner + agent + `status = 'pending'` + unused + unexpired, so a replay is rejected even inside the token window. The action arguments are never stored in this table.
`app_connections` mirrors Composio, which stays the source of truth for credentials and token refresh. The same toolkits are filtered against the catalog before they reach a session.
`browser_sessions` is the cloud-browser history: the runner writes one row when a turn that opened a session ends (session id, context, action count, closed/failed), and the agent panel lists the newest few with links to their Browserbase replay. Rows older than 25 per agent are pruned on write, and they cascade with the agent.
`browser_logins` is the app's list of sites the owner's Browserbase profile is signed in to. A row is written when `browser_request_login` sees the page stop asking for a sign-in, and deleted when a page this run opened shows a signed-out state (an expired session must not be advertised as saved). The prompt reads it through `listSignedInHosts`; the host is normalized (`www.` stripped) and unique per owner.

## 9. Conventions (IMPORTANT — follow these exactly)

- **Imports:** always `@/` aliases. Never relative `../../`.
- **`cn()` gotcha:** generated components import `cn` from the **`cn` package**, not `@/lib/utils`, even though `components.json` maps utils to `@/lib/utils`. Match the file you are editing; do not "fix" it globally.
- **Brand tokens only (Nov 2026 sweep):** app surfaces carry no raw `blue-*` / `bg-white/xx` / inline `#3b82f6` gradients. Ink and washes are `text-brand-ink`, `bg-brand-soft`, `border-brand-border` / `ring-brand-border`; primary actions are `brand-gradient` with `text-brand-on` (or `bg-primary text-primary-foreground`); status tints stay `emerald` / `amber` / `rose` because those are semantic, not brand. Intentional exceptions: inverse CTAs and type sitting on an `ink-panel` (`app/page.tsx`, `app/(auth)/layout.tsx`), the logo mark, image-legibility gradients, and the per-agent clay tones, which are identity colours rather than theme colours. The chat transcript and its composer share one 680px column (`components/agents/agent-chat.tsx`), so the conversation and the prompt field line up on wide screens.
- **affectUI items live in `components/aui/`** (free, vendored) and `components/aui/pro/` (Pro rebuilds); shadcn/base-ui primitives stay in `components/ui/`. Never move one over the other — the two `button.tsx`, `card.tsx`, etc. are different designs on purpose. Both trees carry their own CSS in a `<style href="…" precedence="default">` tag; dark values must be literal, because `--aui-*` only flips when `.dark` is on `<html>`.
- **UI primitives are `@base-ui/react`, not Radix.** Components take a `render={<element />}` prop for as-child behaviour (used for link buttons).
- **Adding components:** `npx shadcn@latest add <name>`. affectUI components come from its registry: `npx shadcn@latest add @affectui/<name>` (configured in `components.json`). They are single self-contained files with their CSS inside, and each declares its own `--ui-*` variables (`--ui-sel-ink`, `--ui-dpk-surface`, …) with `--aui-*` as the fallback, so theming happens once in `globals.css`: every `--aui-*` token is aliased to the app's shadcn tokens and the neutrals (`--aui-placeholder`, `--aui-border-strong`, `--aui-shadow-card`) are derived with `color-mix` from `--muted-foreground` / `--foreground` / `--border`, so all seven palettes and both appearances retint them without per-palette rules. Recolour one instance by setting its `--ui-*` variable on a wrapper, per the affectUI theming docs. Dark mode follows `.dark` (next-themes) and also `[data-theme="dark"]`, which the components check themselves.
